# Operations and recovery runbook

PoPify remains mock-only and single-store. No production deployment is authorized by this repository.

- GET /live checks application liveness; GET /ready checks order schema access and an active managed admin where applicable. /health retains its existing database health contract. Readiness is not an end-to-end n8n availability assertion.
- GET /api/ops/status requires an authenticated operator and reports counts, oldest queue age, uncertain approvals and recent persisted worker polls. It contains no customer payloads. A stale poll does not prove the n8n process is down. Poll it through a protected monitor, not a public endpoint.
- Alert on sustained 503 responses, stale worker polls (three minutes), queue growth, oldest-item age, database pressure and unresolved ambiguous actions. Proposed pilot objectives: p95 webhook acknowledgement <=500 ms and normal queue waiting <=120 seconds under an agreed representative workload. Measure both independently.
- Acknowledged deliveries must persist. If n8n is interrupted, leave queued records intact, restore connectivity and verify normal processing and audit events. Never blindly replay an uncertain action.
- For backups, run PostgreSQL pg_dump -Fc under a least-privilege backup identity, encrypt archives using managed encryption and retain offsite according to an approved policy. Preserve n8n state, encryption key, workflow exports and application configuration separately. Restore to an isolated database, apply compatible migrations, revoke all restored sessions, rotate credentials as appropriate, and check persisted delivery, approval and execution history before resuming workers. Do not restore over the live database. External actions must remain disabled until provider state is reconciled.
- The CI-only scripts/verify_restore.sh creates a unique temporary database in a disposable Compose stack, dumps the source, restores the archive, compares business record counts and removes only its own restore database/archive. This is a basic logical restore drill, not offsite/PITR evidence. Stop mutating workers during a manual consistency drill.
- New signed webhook deliveries persist an allowlist of order fields used by PoPify. Full addresses, line items and unrelated notes are excluded. Historical records and approval snapshots are not rewritten. Email, support text and audit evidence remain personal data; establish retention, access and deletion procedures before real data use. OpenAI requests now set store=false; this does not promise zero provider retention or complete anonymization.
- Before staging, verify managed identity and role changes, login limits with trusted proxy configuration, TLS, private worker access, request timeouts, distributed ingress traffic controls, accessible workflows, restore objectives and workload measurements. Do not expose the local n8n editor. Before real data, approve retention, backup encryption and privacy procedures. Before provider execution, verify provider-specific idempotency and reconciliation. All live actions stay disabled.

## Ingress and interruption verification

The example deploy/public-webhook.nginx.conf serves TLS on 8443 and exposes only the signed order webhook. Its IP and global limits are provisional and must be tuned to verified traffic and trusted proxy configuration. All console/internal routes return 404 at this public boundary. Use a separate private HTTPS operator ingress with identity controls, never expose n8n's editor, and configure Uvicorn to trust forwarded headers only from a known proxy address. Use trusted real certificates in actual staging. Do not use the generated CI certificate or expose the Compose API port publicly. App mutation concurrency is capped per process and body reads have a 15-second deadline; edge controls still matter for multiple processes and slow connections.

CI runs an isolated ingress smoke test (including a bounded synthetic request burst), pauses n8n and restarts the API with a durable queued record, observes scheduled recovery, interrupts the database, checks liveness/readiness, and restores a disposable dump. It also runs Chromium/axe against the isolated synthetic preview, gating selected structural rules and retaining the complete automated violation report. Review the full report; manually verify screen readers, focus order, contrast, role-specific workflows, zoom and keyboard completion. Automated reports are not accessibility conformance certification.

For representative performance, use the existing benchmark for in-process database/service measurements and the scheduled interruption exercise for observed recovery duration, which includes the deliberate outage. Neither measures sustained production network load. Before increasing worker concurrency or batches, measure arrival rates, p95 queue age, retry traffic, backlog drain, query plans and database saturation under a disposable representative workload.

Run `python -m scripts.privacy_inventory --older-than-days 90` from the authorized deployment terminal to obtain a read-only aggregate retention inventory. The threshold is a reporting parameter, not a default retention policy. Do not delete historical approvals, payloads or audit evidence until retention and replay obligations are resolved. Container Uvicorn access logs are disabled because the application records sanitized route templates, status, duration and correlation IDs; review gateway/error logs separately.

The ingress smoke check prints only expected and actual HTTP status codes and aggregate burst status counts. Example TLS keys are generated for disposable CI only. Keep the public ingress and operator ingress separate.

The production-configuration PostgreSQL verifier uses a disposable schema, managed accounts and an HTTPS in-process TestClient. It verifies secure-cookie attributes, role enforcement, attributable support triage and approval, mock execution, readiness and revocation without performing a real TLS deployment. The separate ingress smoke test verifies local TLS termination. CI browser checks now gate contrast and inline-link distinguishability in addition to the selected structural rules after review of the observed axe report.

The Operations screen and protected API distinguish due items, future retries, exhausted work and unresolved provider outcomes. Worker state distinguishes stale polls from a recent failed poll; preview intentionally disables worker alarms. `python -m scripts.check_operations` emits aggregate JSON and exits 0 for healthy, 1 for attention, 2 for unavailable. Configure a trusted scheduler to collect exit codes and route changes to an approved alert destination; no external notification is sent by default. Initial eligible queue age threshold is 120 seconds; worker poll staleness is 180 seconds. These are proposed operating thresholds, not measured SLAs.

The scheduled-workload verifier submits four signed synthetic orders at 35-second intervals over HTTP, retries each delivery and support intake idempotently, waits for real scheduled n8n processing, and checks a delayed-order exception remains pending. It reports acknowledgment latency, order and support queue p50/p95/max, elapsed time and observed completion rate. A 420-second drain guard prevents unbounded CI; this is a low-rate scheduling exercise, not a saturation or merchant workload test. The restore drill compares record-content digests in its small quiescent database, checks session restoration and removes restored sessions/login buckets only in the isolated target, measuring elapsed time. No digest or record content is printed.

## Private mock-only staging profile

The optional `deploy/staging.compose.yml` overlay requires a current Compose release supporting `!reset`. It removes API/n8n host port mappings, keeps PostgreSQL private, enforces managed identities, secure cookies and mock-only operation, and exposes only the operator TLS gateway on loopback port 8444. Provision the `.env` with unique random app, worker, PostgreSQL and n8n encryption secrets; supply `POPIFY_STAGING_TLS_DIR` with `tls.crt` and `tls.key` from your approved certificate authority. Run `docker compose -f docker-compose.yml -f deploy/staging.compose.yml up --build -d` only on an authorized isolated host. Use the trusted CLI to provision an administrator, check `/ready`, and verify private networking before granting access. The profile disables Shopify intake and external AI and does not enable live actions. Access remotely only via approved private networking; do not publish the gateway or use CI certificates outside CI. The app uses conservative proxy defaults; without an explicitly trusted proxy, the gateway address may share the application login budget. Configure trusted forwarded headers only after verifying the network boundary. CI exercises actual HTTPS with a disposable trusted certificate, role denial, cookie attributes, session revocation, route isolation and port bindings. This is not evidence of an external staging deployment.

The production-configuration PostgreSQL verifier also exercises ambiguous outcomes, denied blind retry, duplicate reconciliation, reviewer-attributed nonexecution assertion, fresh human approval and delayed transient retry through the actual HTTP contracts. A previously persisted started execution is converted to an explicit ambiguous outcome and never redispatched by the worker. The tests use synthetic mock outcomes, not actual provider submissions.

For an authorized host, `bash scripts/backup_encrypted.sh VERIFIED_RECIPIENT_FINGERPRINT /approved/private/path/backup.gpg` streams a custom-format PostgreSQL dump into GPG encryption and publishes the encrypted file without overwriting an existing backup. Confirm the recipient fingerprint independently, protect the recipient private key outside the host, and use an appropriately restricted database backup identity; the supplied Compose helper uses the configured database container account. No upload is performed. Use `COMPOSE_FILE` for an approved overlay. CI generates an ephemeral recipient, verifies no-clobber behavior, decrypts into an isolated restore target, compares record content and revokes restored sessions. Production restore, offsite transfer, key recovery, n8n state backup and approved retention schedules are separate operational gates.

Login processing has its own per-process four-request concurrency budget within the global mutation cap. Signed webhook database work runs in the synchronous worker pool rather than blocking the ASGI event loop. These limits are defense-in-depth, not a replacement for a trusted ingress and capacity testing. CI runs once per PR update and on main pushes (plus manual dispatch) instead of duplicating every feature-branch push.

The PostgreSQL interruption exercise now tests a signed intake request during the outage (503 with Retry-After, no acknowledgement, responsive liveness) and replays the same synthetic request after recovery (one durable delivery and order, duplicate-safe processing). The private staging job additionally exercises managed administrator and auditor browser journeys and scans their screens with axe. The scanner context bypasses the disposable certificate and CSP solely for instrumentation; the preceding HTTPS smoke test independently validates certificate trust and CSP headers.

For scheduled alert routing use `python -m scripts.check_operations --state-file /private/monitor/popify.json --repeat-seconds 900`. The state directory must be owned by the monitor account and private; each environment needs a separate state file. The command atomically records opened, resolved and reminder transitions, while an unavailable database does not falsely resolve outstanding business alerts. The state contains only bounded alert codes and timestamps. Route transitions (not every poll) to an approved notification destination and alert on monitor failure/absence through the scheduler itself. The command emits no external notification and makes no claim about delivered alerts.

A measured four-order workload on the single-item schedule (CI run 45942903311) completed eight order/support items in 288.858 seconds (1.662 combined completions/min), with actual HTTP acknowledgment p95 8.821 ms, order queue p95 133.218 s and support queue p95 47.327 s. Order p95 exceeded the proposed 120-second target. The n8n order workflow now requests three due deliveries per poll, with a bounded API range 1–5 and a seven-second between-item budget; the legacy no-parameter call remains single-item. Each item commits and releases its lock separately; failed items retain backoff. Re-run the same synthetic workload and compare actual measurements. The small order workload now gates its observed p95 at 120 seconds; this is not a sustained production SLA. The support schedule remains unchanged pending representative evidence.

CI separates the real scheduled workload into a dedicated job and uploads its measured output, so a queue-performance failure cannot prevent interruption or encrypted-restore checks from running. Database migrations are serialized with a PostgreSQL transaction advisory lock before creating the migration ledger; the verification suite exercises two competing migrators on a fresh isolated schema. This is startup race protection, not authorization for concurrent production deployment or schema rollback.

Run 45943883804 verified order batching (order p95 51.231s, support p95 166.858s, HTTP acknowledgement p95 13.369ms). Support batching now uses the same bounded per-item transaction helper, only in mock mode; external AI remains single-item. CI extends the workload to 12 paired orders/inquiries over 25-second arrival intervals and measures observed peak backlog, end-to-end latency and both queue p95s. Proposed synthetic gates: <=120s for each queue and <=500ms acknowledgement. This is not a merchant load model or a production SLA.

### n8n state recovery
For an approved maintenance window, stop n8n cleanly and run `bash scripts/backup_n8n_encrypted.sh VERIFIED_RECIPIENT_FINGERPRINT /private/path/n8n.gpg`. Preserve the exact n8n image version and matching encryption key separately; do not restart n8n while archiving. This copies the stopped SQLite state, workflow publication marker and other n8n files into an encrypted no-clobber archive. Do not restore over the original volume. The disposable CI drill restores to a newly named volume, compares database/marker digests, verifies the running container uses the restored volume, checks a durable queued order is processed by the actual schedule, and confirms the original volume is unchanged. Before any operational restore, stop external actions, independently validate archive provenance, align business database and n8n state recovery points, rotate/revoke restored operator sessions and verify workflow/credential configuration. The drill does not prove recovery of live credentials, external storage or offsite key availability. Configure n8n execution pruning at seven days / 10,000 records as a conservative starting point; business audit history remains in PostgreSQL. Review retention with the approved data policy.

Queue counts now use a single aggregate statement per queue so concurrent enqueue/drain cannot produce negative scheduled counts; the Operations screen separates human review backlog from automatic work and timestamps observations. Delivery failure accounting rechecks the retry state after rollback, preventing a competing worker's recorded attempt from being consumed a second time. Unexpected production request errors return a generic correlation-ID-bearing response, log only an error type and correlation ID, and advise checking recorded state before retry; development retains tracebacks for debugging. Monitor the structured unexpected_request_failure event via the approved log collector; never log raw customer payloads.

For reliable local handoff to a notification relay, prefer `python -m scripts.check_operations --outbox-file /private/monitor/outbox.json`. The pending_events array is durable across process restarts and contains event_id, transition, code and timestamps; repeated polling returns unacknowledged events. Only after the approved relay confirms delivery, acknowledge each event with `python -m scripts.check_operations --outbox-file /private/monitor/outbox.json --ack-event EVENT_ID`. Acknowledgement is idempotent and independent of database availability. The relay must deduplicate by event_id (at-least-once handoff, not exactly-once delivery). A full 500-event outbox fails visibly without discarding events; monitor exit 2 and intervene. Use a private persistent directory and a single designated relay. Existing --state-file mode remains compatible but is not durable delivery handoff. External destination, routing and acceptance remain unverified. Operations now displays last successful and failed worker activity separately from the last poll.

Store allowlists are canonicalized to a single valid myshopify.com DNS hostname; malformed signed host headers are rejected. If a support reference and email match multiple order records in the configured store, triage returns no matching facts and requires human verification instead of choosing an arbitrary order. PostgreSQL recovery additionally compares schema migration history, session/login-bucket content and sequence state before removing restored session and login-budget rows. The hosted Ubuntu 24.04 browser jobs install pinned Chromium without updating unrelated system package repositories; actual browser launch remains mandatory. Local environments may need Playwright system dependencies installed separately.

Readiness validates mapped columns using zero-row queries and active administrator availability where managed identity is enabled. A partial schema cannot be reported ready simply because primary-key columns exist. The public-ingress CI harness now uses a trusted disposable certificate with localhost SAN, performs signed intake and duplicate replay through TLS, and verifies exactly one persisted delivery before exercising malformed/oversized and rate-limited traffic. The public gateway remains an example boundary, not an authorized public deployment.

The private staging profile separates the PostgreSQL data plane, internal n8n worker plane and operator gateway plane. The API is the only service attached to all three. CI inspects actual container network membership and verifies that n8n can resolve the API but cannot resolve the database. This is defense in depth; do not expose or connect these networks to an unapproved host. The restored n8n exercise now also submits an idempotent synthetic support inquiry against the restored delayed order, verifies the support and exception schedules create unique pending approvals, and proves no mock or external action executes without approval.

The verified 2895765 baseline (run 45945917584) measured 12 pairs at 25s arrivals: order p95 56.852s, support p95 47.817s, receipt-to-draft p95 104.908s, 4.356 combined completions/min. Scheduled CI now runs independent steady and overload profiles: 12 pairs at 25s and 18 pairs at 10s respectively. The overload arrival rate intentionally exceeds the nominal three orders/minute; require observed backlog growth, eventual complete drainage within 540s, no duplicate or unapproved actions, and HTTP ack p95 <=500ms. The steady profile retains both 120s queue gates. Record actual backlog samples and drain time, not a production capacity claim.

Disposable encrypted restore drills now import the ephemeral synthetic secret key into a distinct recovery keyring, confirm that an empty keyring cannot decrypt, reject truncated ciphertext, and complete GPG integrity verification before restoring to isolated targets. Backup publication uses GNU ln -T for atomic no-clobber semantics even when the requested output is a directory. These scripts target Linux hosts with GNU coreutils; set COMPOSE_FILE to the approved profile where applicable. Do not export a real secret key with the CI helper. Actual custodian recovery, archive authenticity/provenance, independent storage, and approved host-loss RPO/RTO still require separate evidence.

Run `python -m scripts.privacy_inventory --older-than-days 30` for a count-only inventory including execution/reconciliation evidence and expired authentication artifacts. Run `python -m scripts.prune_identity` for a dry run; `--apply` deletes only expired session hashes and expired login-rate buckets under the login/account-management lock. Active sessions, accounts, business records and audit history are untouched. Schedule only on an approved host. Business retention/deletion remains policy-gated because orders, support cases, approval snapshots, replay keys and reconciliation evidence are linked.

The monitor now reports handoff status, pending event count and oldest pending age. Exit 1 also means undelivered events remain even when business conditions are healthy; exit 2 indicates unavailable monitoring or invalid state. The live Compose outage drill verifies durable opening, deduplication, acknowledgement without PostgreSQL, and a distinct resolution event after recovery. External notification delivery is still an independent gate.

### Scheduled overload baseline and bounded capacity increment
Run 45949788298 (c9ec4f0) passed all seven jobs. Steady 24-item p95s: order 57.804s, support 47.816s, end-to-end 105.814s, HTTP ack 16.626ms. Overload 36 items at 10s arrivals: order p95 192.491s, support 47.805s, end-to-end 240.497s, HTTP ack 17.880ms, peak order backlog 11, support backlog 3, 391.613s total, 220.632s from last order submission to full downstream drain, 5.516 combined completions/min. No queued backlog remained and no unapproved actions executed. Increase both mock scheduled batch requests from three to five (existing API maximum), without increasing concurrency or changing the one-minute schedule. External AI remains single-item. The existing steady gates remain; the comparable overload profile adds a provisional order p95 regression gate of 180s, retaining the 540s complete drainage deadline. The arrival rate is still above nominal capacity; do not interpret this as a saturation or production SLA. Review exact-head measured results before claiming improvement.

A repeated signed delivery ID now returns 200 only when the canonical store, topic and minimized order input match the persisted record (and event IDs agree when both are present). Conflicting reuse returns 409 and records a content-free audit event; the original record is unchanged, including the concurrent-insert fallback. Exact duplicate acknowledgements remain compatible. This is local input integrity, not a claim about Shopify's externally verified retry semantics.

Managed private staging Chromium now exercises all four operator roles, actual scheduled support triage, support's denied approval request, reviewer rejection and approval, actual scheduled mock execution and durable audit attribution. CSP stays enabled for app interactions; axe is evaluated through the test browser's DevTools instrumentation. CI checks the saved case/approval/execution records, including no execution for rejected work. The support form explains that only reviewers or administrators can decide. Queue tables explicitly declare column headers for assistive technology. Manual screen-reader review remains a release gate.

Monitoring now distinguishes persisted execution attempts without terminal outcomes (critical; never blindly replay) from approvals requiring reconciliation, and alerts when pending human review exceeds HUMAN_REVIEW_ALERT_SECONDS (default 86400, provisional, tune with the operator). Counts are separate so operators should not sum them as unique cases. No customer payloads or execution identifiers are exposed in the operational snapshot. Do not interpret the human-review threshold as a worker latency SLA or an instruction to bypass approval.
