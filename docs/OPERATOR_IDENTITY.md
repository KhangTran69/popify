# Managed operator identities

Local development and isolated preview retain the existing configured demo login. Production now requires PostgreSQL and MANAGED_IDENTITY=true; the old shared operator login cannot be used in production. Apply migrations before starting. Account creation is performed by a trusted deployment administrator using an interactive terminal (no public account registration).

    docker compose exec api python -m scripts.manage_operators create alice --role admin
    docker compose exec api python -m scripts.manage_operators create bob --role support
    docker compose exec api python -m scripts.manage_operators create carol --role reviewer
    docker compose exec api python -m scripts.manage_operators create dana --role auditor

Use unique strong passwords. Names are stable audit identifiers and cannot be reused. The CLI supports password, role, disable, enable and revoke; all account changes revoke existing sessions. Logout revokes the server-side session. Sessions expire after eight hours; at most five active sessions are retained per account; tokens are random and only SHA-256 digests are stored. Passwords are stored using salted PBKDF2-HMAC-SHA256 (600,000 iterations). Login failure budgets are persisted and serialized across PostgreSQL processes; the local preview uses its existing behavior. A legitimate user may be temporarily blocked after repeated failures; investigate abuse before changing limits. Deploy a gateway with request timeouts, global and per-client traffic limits and trusted proxy configuration; these database-backed budgets are not a complete edge protection solution.

Roles: admin can perform every existing operation; support can create inquiries and retry support triage; reviewer can approve/reject, refresh, reconcile and retry approved actions; auditor is read-only. All four can view single-store operational data. No tenant isolation or field-level privacy segmentation is claimed. Role changes take effect on subsequent requests; already-running requests are not cancelled. The deployment CLI is privileged and its events identify deployment_admin, not a verified OS account. Use separately controlled deployment access and audit logs. MFA/SSO, independent review and managed identity-provider integration remain production gates if required by the merchant.

For production use COOKIE_SECURE=true, MANAGED_IDENTITY=true, PostgreSQL, unique secrets and protected HTTPS ingress. A configured Shopify secret also requires a store domain allowlist. External AI in production requires ALLOW_EXTERNAL_AI=true after the data-processing review; mock remains the default. Never expose the n8n editor or internal API publicly.

The existing approval actors and historical records are preserved. New human support intake records the verified operator username; integration intake identifies the shared integration principal, not an individual. Tests cover unauthorized role mutations, logout cookie replay, role revocation, expiry and persistent login budgets. CI exercises PostgreSQL concurrent login budgets and cross-session revocation. Manual role-based browser evaluation, MFA/SSO as applicable, and deployed edge controls remain separate verification requirements.

Managed administrators can open `/operators` to inspect account roles, enable/disable access, change roles and revoke sessions. The controls are CSRF-protected and audit the authenticated administrator username. Administrators cannot modify their own account through this page, and the last active administrator cannot be disabled or demoted through the console. Account creation and password resets remain in the privileged CLI, with deployment-admin attribution. The CLI is also the break-glass recovery path.

The production-configuration CI verifier exercises the actual HTTP routes using PostgreSQL, including support-agent intake, reviewer-only approval, mock execution and session replay rejection. It uses synthetic credentials and an in-process HTTPS client; a real deployment still requires a trusted private HTTPS ingress and appropriate identity assurance.

Successful reauthentication replaces the presented server-side session, including account switches. The administrator mutation checks the current session again under the account-management lock, preventing a revoked administrator from changing accounts after waiting for that lock. Other already-running business requests retain the documented in-flight semantics.

Managed identity now resolves account/session validity in one database statement. Ordinary PostgreSQL operator mutations lock the account then the session for the transaction, so account revocation or role changes serialize against an already authorized mutation; subsequent requests using the old session fail. This does not cancel a mutation already committed or an independently authorized queued action. Account administration retains its existing advisory-lock/revalidation path. CSRF tokens remain mandatory; managed cross-site form requests with Sec-Fetch-Site: cross-site are additionally rejected. Older clients without that header still require the session-bound token.
